# МИН — самостоятельный мессенджер в KONTUR Web

`МИН` — пародия на MAX с названием, построенным на противоположности `MAX ↔ MIN`.

## Архитектура

МИН не использует игровое сохранение, игровые часы, дни недели или scripted-ответы. Его данные хранятся отдельно:

```text
localStorage: until-friday-min-messenger-v1
IndexedDB: until-friday-min-media-v1
BroadcastChannel: until-friday-min-sync-v1
MIN-ID: until-friday-min-peer-id-v1
```

Клиент состоит из двух уровней:

1. local-first мессенджер, который работает без сервера;
2. P2P-сеть PeerJS/WebRTC для прямой связи двух открытых браузеров.

## Локальные функции

- произвольная отправка сообщений;
- личные чаты;
- группы;
- каналы;
- избранное;
- контакты;
- папки чатов;
- непрочитанные сообщения;
- черновики;
- ответы;
- пересылка;
- редактирование;
- удаление;
- реакции;
- закрепление сообщений и чатов;
- архив и отключение уведомлений;
- поиск по чатам, сообщениям и контактам;
- изображения, видео, аудио и обычные файлы через IndexedDB;
- запись голосового сообщения через MediaRecorder;
- экспорт и импорт резервной копии;
- синхронизация состояния между вкладками одного браузера;
- независимый профиль и настройки.

## Реальная связь между браузерами

Каждый клиент получает собственный `MIN-ID`. Пользователь передаёт его собеседнику, после чего второй клиент подключается к этому идентификатору.

Пока оба браузера открыты и находятся в сети, работают:

- двусторонние произвольные сообщения;
- обновление отредактированных и удалённых сообщений;
- реакции;
- передача изображений, видео, аудио и обычных файлов;
- индикатор набора текста;
- аудиозвонки;
- видеозвонки.

PeerJS Cloud используется для поиска браузера по `MIN-ID` и согласования соединения. После установки соединения сообщения, файлы и медиапотоки передаются через WebRTC.

## Ограничения текущего P2P-режима

Это настоящий сетевой обмен, но не полноценная облачная инфраструктура уровня Telegram или MAX.

Сейчас отсутствуют:

- регистрация и пароль;
- подтверждение личности владельца `MIN-ID`;
- офлайн-доставка;
- push-уведомления;
- серверная история;
- восстановление аккаунта;
- синхронизация архива на нескольких устройствах;
- постоянное облачное хранение файлов;
- серверная модерация групп и каналов.

`MIN-ID` нельзя считать доказательством личности. Перед подключением его нужно получить от собеседника через доверенный канал.

## Почему нужен постоянный backend

GitHub Pages раздаёт только статические HTML, CSS и JavaScript. Для полноценного публичного мессенджера отдельный сервер должен предоставить:

1. регистрацию, вход и управление сессиями;
2. пользователей, контакты и поиск по username;
3. серверные личные чаты, группы и каналы;
4. роли владельца и администраторов;
5. хранение сообщений, реакций, закрепов и статусов прочтения;
6. объектное хранилище файлов;
7. WebSocket или Server-Sent Events для офлайн-доставки;
8. собственный PeerServer или другой WebRTC signaling;
9. push-уведомления;
10. rate limit, журнал безопасности и резервное копирование;
11. HTTPS и корректный CORS для GitHub Pages.
